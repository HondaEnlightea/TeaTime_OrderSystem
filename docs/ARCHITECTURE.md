# 技術構成と設計判断

## 比較と採用

| 選択肢 | 判断 |
| --- | --- |
| 既存POS（ERPNext等） | 商品・会計機能はあるが、学祭の受付番号・日本語呼出・独立キッチンへの適合も必要。3日間の期限では小さな専用アプリの方が確認範囲を限定できると判断 |
| クラウドWebアプリ＋共有DB | 外部通信・アカウント・ホスティングが必要。独立したローカル最低構成を満たさないため今回は採用しない |
| ブラウザのlocalStorageだけ | 独立端末の簡易保存は可能だが、共有時の採番・バックアップ・状態競合を扱いにくい |
| **Node.js＋SQLite＋ブラウザ** | **採用。** 同じアプリを会計専用・キッチン専用の独立モード、単一サーバーでの連携モードとして起動 |

既存POSの比較根拠：[ERPNext公式POS設定](https://docs.frappe.io/erpnext/point-of-sale/setup)。全製品の網羅的比較ではなく、本件固有機能と短い期限を踏まえた実装判断です。

## 構成と運用モード

Node.js 24.14以降の24系の標準HTTP・SQLite・暗号・テスト機能を使用します。HTML/CSS/JavaScriptはビルド不要、外部CDN・フォント・ライブラリ不要。Node.js 24.14.1のSQLite APIはExperimentalWarningを表示します。利用APIを24系に固定して検証します。

ローカル起動（start-local.cmd / npm start）では、このPCの用途を会計専用かキッチン専用から選択します。指定なしで共有モードには入りません。独立モードで別の係の画面を開いた場合は、この端末の担当画面へ戻します。

独立運用は会計PCとキッチンPCのそれぞれにサーバーとDBを置き、127.0.0.1だけで待ち受けます。独立会計の注文には `fulfillment=0` を保存し、金額と採番だけを管理します。完成・提供状態を管理せず、未提供が残って営業回切替を妨げることもありません。独立キッチンは紙の会計番号を `source=paper` の注文として保存し、合計0・明細なしで売上から除外します。必要な紙の注文内容は備考へ記録できます。提供状態・呼出・履歴は連携と同じ仕組みです。

連携運用はキッチンPCのサーバー・DBだけで採番・保存します。会計スマホ/PCとキッチンのUIは分離しますが、APIと記録は共有します。2つの独立DB間の自動同期・自動合流は行いません。ネットワーク故障時の切替手順は運用文書に記載しています。

公開番号画面は1秒、スタッフ画面は1.5秒間隔で更新。スタッフだけに固定された切断警告を表示し、公開番号画面は警告を出さず最終番号を保持します。公開APIに金額・茶葉・備考・端末割り当てを返しません。

参考：[Node.js HTTP API](https://nodejs.org/docs/latest-v24.x/api/http.html)、[SQLiteトランザクション](https://www.sqlite.org/lang_transaction.html)。

## 採番・料金・再送

採番・注文明細・履歴・次番号を `BEGIN IMMEDIATE` のトランザクションにまとめ、営業回＋番号の一意制約で重複を防ぎます。独立キッチンの手入力もこの制約で拒否します。営業回の開始番号は明示指定できます。

初期メニューは `config/menu.json` の提供表からお茶28品を読み込みます。紅茶23品・日本茶など5品、価格帯は300/400/500/600円です。ミルク・アイスの2行は追加オプションとして保存し、単独のお茶には含めません。氷とミルクの真偽を明細識別に含め、同じ茶葉の異なるオプションを別行で保存します。追加料金はサーバーで各50円/杯に固定し、クライアントから送られた金額を信用しません。登録時の名前・基本価格・オプション料金を複写して、過去の売上を保持します。

登録識別子とペイロードのハッシュを保存します。同じ内容の再送は元の番号を返し、同じ識別子で内容を変更すると拒否します。ブラウザは未確認登録を保存して入力を固定します。営業回・メニュー改訂番号は確認画面を開いた時点で固定し、登録までに変更された場合は再確認します。

## 会計の1杯ずつ入力・トップの番号表示入口（v11 / 2026-10-15）

会計の編集中カートと確認画面は、茶葉ボタンを押すごとにquantity=1の別行を追加します。オプション変更は選んだ行だけに適用し、同じ内容になっても編集中は統合しません。削除も1杯単位です。旧下書きのquantityを1杯ずつ復元し、再送待ちの確定ペイロードは書き換えません。

新規の確認ペイロードを作る時点でだけ、茶葉ID・氷・ミルクをキーに数量を合計します。これにより従来のサーバーの重複明細検証、1組99杯制限、LAN切断時の端末保存、注文明細・キッチン・売上集計を保ちます。金額の正式計算は引き続きサーバー側です。

連携のトップでは会計・キッチン・番号表示を同列の入口にし、番号表示は /display?setup=1 を新しいタブで開きます。既存のキッチン画面上部の番号表示リンクと公開画面/APIの情報制限は変更しません。

## 状態・音声

通常は `waiting → ready → served`。理由付きで未提供を取消できます。完成の競合を検出し、同じ状態変更から音声イベントを二重生成しません。会計専用の記録は完成・提供へ遷移できず、取消だけを扱います。

表示ウィンドウ1つが15秒の担当期限を取得し、5秒ごとに更新します。音声イベントは再生前に取得済みと記録し、同じイベントの自動重複を防止します。担当が停止・失敗した場合に「必ず1回聞こえる」ことは保証できないため、未確認・失敗をスタッフが確認して明示的に再呼出します。通常の再生中には失敗扱いを表示せず、35秒超過・担当期限切れ・失敗応答を検出します。

Web Audioの2音チャイムは緩やかな立上りを保ちながら旧版より強くし、終了後350ms待ちます。番号画面を先に更新し、同じ営業回で提供可能な対象だけ「受け付け番号〇〇のお客様」と読み上げます。チャイム中に提供済みになれば読み上げません。開始・受付・提供済みでは自動発声しません。

ブラウザが公開する日本語音声のうちGoogleを優先し、手動選択を保存します。Google音声の搭載・ネット接続要否は実機確認が必要です。端末内の日本語音声を予備にできます。[利用可能な声の取得](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/getVoices)、[読み上げの音量](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesisUtterance/volume)。

表示内の音量パネルに声選択・チャイム/声の音量・テスト・開始/停止を集約します。読み上げ音量は0〜1、チャイムは独立したゲイン制御。選択・音量は端末に保存します。別アプリのBGMの音量は操作しません。ユーザー操作で音声を解放し、更新後は明示的に再開始します。

## 保存・移行・保護

SQLiteのWAL・synchronous=FULLを使用。VACUUM INTOで整合した単一ファイルをバックアップします。旧版の明細テーブルを移行し、既存価格・番号・状態・履歴を保持します。旧明細の氷・ミルクはnull（未記録）。旧版の5種サンプルまたは30枠が未変更の場合だけ、提供メニュー28品へ更新します。編集済みのメニューは置き換えません。

モード別のDB・バックアップを使用し、異なる目的の記録を混ぜません。起動オプションで会計APIと紙番号APIの利用可否を制限します。ユーザーの指定により、全モードでPIN・ログイン・認証Cookieを廃止します。書込APIのOrigin検証、Host検証、入力検証、送信サイズ制限、限定ファイル配信は維持します。LANでは接続できる端末から業務画面/APIを操作できます。旧DBのPIN設定は無視し、注文を保持します。一般公開・HTTPS・オンライン決済・個別スタッフ権限は今回の対象外です。

受付番号はArialを優先する太いゴシック系、等幅・ライニング数字を使用します。完成番号はサイズも拡大し、準備中の左22%配置を維持します。フォントの外部取得は不要です。

2026-10-15の操作性改善（v10）：キッチンの準備中・お渡し待ちカードだけを対象に、茶葉名18px/太字、数量22px、オプション14pxへ拡大し、明細間に区切りを追加しました。会計のお預かり欄には高さ52pxの数字・クリア・1桁削除キーを追加し、既存の入力状態・保存・釣銭計算へ接続します。再送内容固定中・登録処理中はテンキーも無効化し、金額上限と既存サーバー検証は保ちます。API・保存形式・採番・音声処理は変更しません。



## 会計管理タブと杯数別売上（v5）

会計に注文履歴・売り上げ・メニュー変更・スタッフ用メニュー表を追加。会計用メニュー編集は営業設定から移動しました。独立キッチンの番号管理・独立DB・音声運用は維持しています。

商品に説明（2000文字以内）を追加する移行は列追加のみで、注文・明細・価格・番号・履歴を書き換えません。旧クライアントが説明を省略してメニューを保存した場合も、IDが一致する商品の説明を保ちます。名前・基本価格・氷/ミルク料金は注文明細のスナップショットが集計の基準です。

集計は取消以外の会計注文だけを使用し、茶葉IDと注文当時の名前別、1注文の杯数別にまとめます。茶葉が改名された場合は当時の名前の別行に残ります。CSVは選択営業回のUTF-8 BOM付き、既存の数式対策を適用します。紙番号登録は売上・販売杯数へ入りません。

入力サイズは注文など64KiB、30〜50件の日本語説明を保存するメニュー更新のみ400KiBです。最大50商品、説明2000文字の個別検証と改訂番号の競合検証は維持します。編集中のメニュー・説明は定期更新で作り直さず、保存中は入力を止めます。

端末用入口 `/portal` は接続確認・時刻・運用モードと担当画面へのリンクを返し、注文内容・売上・備考を出さず、DBを変更しません。LAN起動時にネットワーク候補ごとの入口URLを出力します。旧 `/connection-check` は廃止し、共通の404応答を返します。転送先や新URLは案内しません。

## メニュー説明・アレルギー情報（v6）

画面名を「スタッフ用メニュー表」から「メニュー説明」へ変更しました。既存の /staff-menu 接続先は保ちます。商品に allergens（自由記述500文字以内、初期値は空欄）を列追加し、メニュー変更で編集、メニュー説明で表示・検索します。原材料や追加オプションの実物情報から自動推定しません。未入力の表示は「未確認」です。

商品説明と同様、旧クライアントが allergens を省略して保存した場合は既存値を保持し、明示的な空文字で消せます。改訂番号による同時編集の競合検証を保ちます。商品説明のみの更新でもアレルギー情報を保持します。注文の採番・金額・履歴・お客様番号APIは変更していません。

## LAN起動案内の改善（2026-10-14）

連携起動の最初のURLを /cashier から /kitchen に変更し、親機自身で使うキッチン・番号表示・音声準備の完全なURLをまとめて表示します。会計端末向けは各IPv4候補の接続名付きで別枠に表示します。IPv6・内部ループバック・重複IPを候補から除外します。候補はネットワークインターフェースの列挙であり、接続できることを自動判定したものではありません。

サーバーの待受、Host/Origin検証、保存先、注文共有・独立モードの処理は保ちます。複数ネットワークのどちらを利用するかは、会計端末が接続するネットワークと通信確認ページの結果に基づいて選びます。

### 3台構成の起動案内・接続確認導線（v8 / 2026-10-15）

LANの起動案内は、親機用127.0.0.1と接続名付きIPv4の各候補に、会計・キッチン・番号表示の3リンクを同じ順番で出します。番号表示は /display?setup=1 に統合して音声準備パネルを開き、各候補には別途 /connection-check を表示します。サーバーの起動は親機1台だけで、どの端末でどの業務画面を開くかを分離できます。

通信確認ページは注文やDBを変更しないGETのまま、会計・番号表示への相対リンクを追加しました。ブラウザが確認したオリジン（ホスト・ポート）を保持します。独立モードではその担当で利用できる画面だけを案内し、別担当へのリダイレクトに依存した導線は出しません。Host/Origin検証・公開番号API・音声開始の利用者操作は維持します。

## LAN切断中の会計（v7）

2026-10-15の配置調整（v9）：予備番号・未同期件数と補助操作は、注文入力欄から直近の注文履歴の下へ移動しました。情報を非表示にせず、会計操作を先に配置します。同じ表示要素・イベント処理を使い、右上の固定警告と受付・同期の処理は維持します。

親機が営業回・端末ごとに50件の予備番号をトランザクションで割り当て、次番号を進めます。割り当て自体の再送も同じ識別子で冪等です。未使用番号を他端末へ再利用しません。親機が唯一の採番元であることは維持し、ブラウザでは割り当て済み番号だけを使用します。

割り当てにはサーバー側で固定したメニュー名・販売可否・価格・オプション料金・改訂番号を保存します。端末はIndexedDBの同一トランザクションで番号の消費と会計を保存し、成功後に控えを表示します。同じ接続先の別タブも保存を共有し、BroadcastChannelで変更を通知します。端末保存が失敗した場合は受付完了にしません。売上とCSVは親機の最終状態と自端末の未同期記録を同じ集計関数でまとめます。

復帰時の注文は元の識別子・割り当て番号で再送します。親機は自分の割り当て表から料金を再計算し、端末の引用合計との一致を検証します。LANキッチンの手入力済み紙番号があれば、同じ注文IDに会計・明細・監査履歴を保存し、状態・完成呼出を作り直しません。別の会計番号と競合すれば保留し、端末記録を消しません。切断中の現金返金は別の冪等な記録で同期し、キッチンで先に提供済みになっていても返金監査を残します。

営業回の切り替えは未提供と未終了の割り当てを検証します。各会計端末が未同期ゼロを確認して利用終了する必要があります。端末の利用終了状態もIndexedDBへ保存し、別タブや再読み込みで自動的に番号を再割り当てしません。再開は「予備番号を追加」を明示操作します。IP・端末変更の復旧JSONは元の注文識別子を照合し、復旧した未使用範囲を新規採番に使いません。

スタッフ画面内の移動は同じページで行うため、切断中も注文・履歴・売上・説明を開けます。通常のHTTPのLAN IPではService Workerの安全なコンテキスト要件を満たさないため、画面を閉じた状態からの完全なオフライン起動は今回実装しません。画面を開いたまま使い、保存済み記録は接続復帰後に再開する構成です。[Service Worker登録の要件（MDN）](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)。外部ホスティング・アカウント・CDNは追加していません。

## 提供メニュー・おすすめオプション（v12 / 2026-10-15）

個人情報を除いた提供表の30行だけを `config/menu.json` に保存しています。`kind` でお茶28品とオプション2品を区別し、名前・価格・茶種・おすすめの原文と空欄を保持します。初期メニューはこのJSONから生成し、既存の仮メニューと異なるIDを用いて、旧下書きが別の商品へ誤って対応しないようにしています。テストで旧IDを使う業務フローは明示した仮メニューを使用し、提供メニュー自体は専用テストで検証します。

商品に `recommendation`（100文字以内、初期値空文字）を追加し、「メニュー説明」でのみ表示・編集します。空欄は未設定で、注文のオプションを自動選択しません。アレルギー情報・説明と同様、旧クライアントの省略時は既存値を保持します。公開番号APIや注文明細・集計におすすめ情報を追加していません。

未編集の旧5品・30枠だけを起動時に移行し、価格・名前・販売状況・説明・アレルギー等が編集済みなら保持します。採番・注文・明細スナップショット・監査・呼出・予備番号の凍結料金は変更しません。編集済みDBには「提供メニューを読み込む」で28品を編集画面へ読み込み、既存の改訂番号検証付き保存を利用します。完全な同名が1件だけなら説明・アレルギー・販売状況を引き継ぎます。読込GET自体はDBを書き換えず、独立キッチンでは利用できません。

## 調査済み説明の補完（v13 / 2026-10-16）

`config/menu-notes.json` に28品の説明・アレルギー情報・照合区分・原材料の確認内容・出典URL・留意点を保存し、元の品目表は保持します。初期カタログはIDと名前の両方が一致したメモだけを取り込みます。出典と照合区分は `docs/MENU_DESCRIPTIONS.md` に一覧化し、商品未特定や茶種の参考と実物確認済みを区別します。今回は実物確認はしていません。

既存DBには `menuNotesRevision` 設定で1回の補完を記録します。空欄・空白だけの説明とアレルギー情報をそれぞれ補い、値が変わったときだけメニュー改訂番号を1つ進めます。同じトランザクション内で記録し、手入力、価格、名前、販売状況、推奨、会計・音声履歴は変更しません。補完後の手入力による空欄への消去も、次回起動で復元しません。

提供メニュー読込では既存の空欄へ調査メモを使い、非空欄の手入力は保持します。更新の保存は既存の競合検証を使います。公開番号APIに説明や原材料情報を追加せず、金額計算・採番・状態遷移・音声処理は維持します。

## 端末用入口・テスト営業の初期化（v14 / 2026-10-16）
